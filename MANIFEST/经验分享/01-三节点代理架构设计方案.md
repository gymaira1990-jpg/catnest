> 面向 AI 智能体和日常开发的自建代理通道 · 全链路设计文档
>
> — GCat · 2026-06-22

---

## 〇、为什么写这篇

AI 智能体（Hermes、Claude Code、Cursor 等）在执行任务时会发起大量网络请求。大部分 LLM API 在国内可以直连，但搜索、Git、论文数据库等「伴生服务」在墙内完全不可达。

这篇文档记录了从单节点代理到三节点分流架构的完整演进过程，包括：

- 节点角色划分与拓扑设计
- VLESS + REALITY + WebSocket 多协议通道
- 后量子加密（VLESS PQ Encryption）
- 域名伪装与 TLS 证书策略
- Clash 客户端订阅与分流规则
- 腾讯云 Lighthouse 防火墙与安全组配置

适合有一台以上云服务器的开发者自建 AI 工作通道。

## 二、节点职责

### 2.1 国内中转节点

**双重角色：网站托管 + 代理中转**

```
入站端口:
  :2081  VLESS+WS  直连通道    全流量 → freedom
  :2082  VLESS+WS  中转通道    GEOSITE:cn → freedom
                              其余 → 加密隧道 → HK

出站:
  → HK   VLESS + REALITY + PQ加密
  → 国内  freedom（直连）
```

路由规则：

| 条件 | 动作 |
|------|------|
| 入站来自直连通道 (2081) | 全部 freedom |
| 目标 IP in 中国 | freedom（本地直连） |
| 目标域名 in 中国 | freedom |
| 其余 | 加密隧道 -> HK |

### 2.2 海外出口节点

```
入站:
  :2087  VLESS + REALITY + PQ加密

回落:
  非 VLESS 流量 → nginx :443 → 个人博客（伪装页）

出站:
  freedom（直接访问海外服务）
```

**REALITY 伪装机制**：当 TLS SNI 或握手不匹配时，自动回落到本地 nginx，返回一个真实网站。深度包检测看到的是正常 HTTPS 流量。

## 三、VLESS 后量子加密（PQ Encryption）

这是 v26.6+ 的核心新能力。在节点间链路外层加一层后量子加密：

```
密钥交换: ML-KEM-768 + X25519 混合（后量子安全）
加密算法: AES-256-GCM / ChaCha20-Poly1305
前向安全: 1-RTT 初始握手 / 0-RTT 复用
流量外观: 随机化头部，与 TLS 1.3 无差别
```

即使未来量子计算机问世，也无法解密历史流量。GFW 即使抓到包，看到的也是不可区分的加密数据流。

**配置（xray-core v26.6+）:**

```json
// 出站端
{
  "protocol": "vless",
  "settings": {
    "vnext": [{ "address": "...", "port": 2087, "users": [{"id": "...", "encryption": "none"}] }],
    "encryption": "native"
  },
  "streamSettings": { "network": "tcp", "security": "reality", ... }
}

// 入站端
{
  "settings": {
    "clients": [{"id": "...", "flow": "xtls-rprx-vision"}],
    "decryption": "none",
    "encryption": "native"
  }
}
```

## 四、Clash 客户端与分流策略

### 4.1 订阅文件结构

通过订阅地址统一管理所有节点，Clash Verge 一键更新。

```yaml
proxies:
  - name: GZ->直连
    type: vless
    server: <国内节点IP>
    port: 2081
    uuid: <UUID>
    network: ws
    ws-opts: { path: "/direct-ws" }
    udp: true

  - name: GZ->HK->世界
    type: vless
    server: <国内节点IP>
    port: 2082
    uuid: <UUID>
    network: ws
    ws-opts: { path: "/vless-ws" }
    udp: true

  - name: HK->直连
    type: vless
    server: <海外节点域名>
    port: 2087
    uuid: <UUID>
    flow: xtls-rprx-vision
    tls: true
    servername: <海外节点域名>
    reality-opts:
      public-key: "<REALITY公钥>"
      short-id: "<shortId>"
    client-fingerprint: chrome
    network: tcp
    udp: true

rules:
  - GEOSITE,cn,DIRECT
  - GEOIP,cn,DIRECT
  - MATCH,Proxy
```

### 4.2 分流逻辑

| 目标 | 路由 | 典型延迟 |
|------|------|----------|
| DeepSeek / 豆包 / 国内 LLM | DIRECT | ~100ms |
| GitHub / GitLab | Proxy | ~500ms |
| Tavily / Google Search | Proxy | ~300ms |
| HuggingFace / PyPI | Proxy | ~500ms |
| Docker Hub | Proxy | ~400ms |
| 百度 / 阿里云 / 国内站 | DIRECT | ~10ms |

**关键原则：LLM API 直连，被墙服务走代理。** LLM API 厂商在国内有部署，直连延迟 100-300ms，走代理反而绕路。

## 五、域名伪装设计

- 海外节点 REALITY 目标域名挂载 Let's Encrypt 真实证书
- 回落页面是真实静态博客（个人笔记风格）
- 名称服务器托管在 Cloudflare，CDN 隐藏源站 IP
- 网站与代理共用服务器（经济性）
- certbot + systemd timer 自动续期

---

## 六、安全组与防火墙

**云安全组（云防火墙）——只开放必要端口：**

| 端口 | 协议 | 用途 |
|------|------|------|
| 22 | TCP | SSH |
| 443 | TCP | HTTPS（网站 + REALITY 回落） |
| 80 | TCP | HTTP（证书验证） |
| 2081 | TCP | 直连通道 |
| 2082 | TCP | 中转通道 |
| 2087 | TCP | REALITY 出口 |

原则：一端口一用途，零多余暴露面。云安全组 + 本地 ufw 双层防护。

## 七、部署软件栈

| 组件 | 用途 | 位置 |
|------|------|------|
| xray-core v26.6+ | 代理核心 | 中转节点 + 出口节点 |
| nginx | 网站 + 伪装回落 | 中转节点 + 出口节点 |
| certbot | TLS 证书自动续期 | 中转节点 + 出口节点 |
| Clash Verge | 客户端分流 | 本地 Windows |
| systemd | 服务管理 | 全节点 |

---

## 八、写在最后

这套架构的核心不是「把所有流量扔给海外节点」，而是**在正确的地方做正确的路由决策**——

1. LLM API 直连（快）
2. 被墙服务走中转（通）
3. 海外出口走 HK（稳）
4. 节点间加 PQ 加密（安全）

特别是对 AI 智能体来说，一天产生的网络请求可能是人的几十倍。让每个请求走最优路径，比盲目上多节点中转有效得多。
